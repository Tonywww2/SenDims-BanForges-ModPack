# 仪式着色器特效设计

日期：2026-11-13。状态：已实装（特供模组 1.1.2），已并入 11-11 补丁包并部署到主整合包；实装与验证见第 12 节，与设计不同的地方以第 12 节为准。

前一版设计：[仪式与基岩破坏者特效设计](仪式与基岩破坏者特效设计-2026-11-03.md)。本设计在前一版的流程和时间线上加一层客户端着色器表现；仪式流程、判定和玩法都不变。

已定：

- 屏幕效果默认全开（传送旋涡、召唤涟漪），客户端配置可以单独关闭。
- 必须与光影兼容：开着光影包时完整显示，不能用"检测到光影就不画"代替兼容。
- 开发环境验证通过后部署到主整合包（特供模组 1.1.1 换成 1.1.2），并入 11-11 补丁包。
- 基岩破坏者一并接入（4.4）。其余定稿见第 11 节。

## 1. 范围

| 仪式 | 脚本 | 本设计 |
| --- | --- | --- |
| 结构召唤：白金地牢、武士X | `spawn_struct.js` | 包含 |

现有表现全部由服务端发原版命令实现：

- 粒子：汇聚、光柱、光环、冲击波、余韵；
- 音效、可视闪电、灾变屏幕震动、副标题；
- 传送门在第 30 tick 给发起者 1.5 秒黑暗。

这些都保留，作为着色器层的陪衬，调整见 5.4。

## 2. 目标

1. **仪式感**：蓄能、释放、余韵三段，每段的光、形、声节奏明确，和现有音效的时间点对齐。光是主角（发光线条、光柱、光幕），粒子做陪衬。
2. **真实感**：
   - 法阵贴着地形画，地面上有一圈光池；
   - 受雾影响，随距离自然淡出；
   - 释放时有冲击波和空气扰动；
   - 开光影时由光影包加上泛光和雾。
3. **光影兼容**：开着 Complementary 等光影包时完整显示，不发黑、不闪烁、不黑屏、不崩溃；不开光影时同样好看。
4. **主题化**：每个仪式有自己的法阵样式和配色。新增仪式只写主题。
5. **玩法不变**：召唤什么、传送到哪里、消耗什么、蓄能多久都不改。服务端只在几个阶段点各发一个小包，画面全在客户端生成。
6. **性能可控**：没有仪式时零开销；仪式期间开销有上限，远处自动降级。

## 3. 光影兼容方案

### 3.1 约束

- 整合包装有 Emberlens 1.8.9（Oculus 分支，带 Iris API），实例里有 Complementary Reimagined 和 Complementary Unbound 两个光影包。
- 光影开启时，Iris 在绘制世界期间把原版着色器程序换成光影包的 gbuffers 程序，再经过光影包的合成通道（光照、雾、泛光、抗锯齿）输出。
- 模组自己注册的着色器如果在绘制世界时直接使用，Iris 无法把它对应到光影包的程序，写出的缓冲和光影包预期的不一致。常见结果有：
  - 发黑、闪烁；
  - 被雾或水面吞掉，或完全不可见；
  - 在阴影通道里多画一次。
- 所以在世界里直接用自写着色器画法阵，光影下不可靠。

### 3.2 做法：自写着色器只在世界绘制之外运行

| 步骤 | 何时 | 用什么画 | 光影下 |
| --- | --- | --- | --- |
| 画布烘焙 | 每帧世界绘制开始前（`RenderTickEvent` START） | 自写着色器，画进离屏画布（帧缓冲纹理） | Iris 此时没有接管，自写着色器正常运行 |
| 世界几何 | 世界绘制中（`RenderLevelStageEvent` 的 `AFTER_PARTICLES`） | 原版发光材质（`RenderType`），把画布当普通纹理贴到面片上 | Iris 认得原版材质，换成光影包的对应程序；法阵自动带上光影的雾、深度、抗锯齿和泛光 |
| 屏幕效果 | 整个世界（含光影最终合成和手持物）画完之后、界面之前 | 自写着色器，处理最终画面 | 处理的是光影合成后的最终图像，不受光影影响 |

要点：

1. **屏幕效果不挂在 Forge 的 `AFTER_LEVEL`**：
   - `AFTER_LEVEL` 在 `LevelRenderer.renderLevel` 内部派发，光影的最终合成要到 `renderLevel` 返回前才做，在 `AFTER_LEVEL` 处理会扭曲到中间缓冲。
   - 改为用 Mixin 挂在 `GameRenderer.render` 里 `renderLevel` 返回之后。这时最终画面已经在主帧缓冲里，界面还没画，所以界面不会被扭曲。
   - 按 F1 隐藏界面时同样生效。
2. **阴影通道不画**：绘制世界几何前先查 Iris 是否在画阴影，复用已有的 `client/performance/IrisShadowPass`；是就跳过，法阵和光柱不投影。
3. **光影开启时压低烘焙光晕**：
   - 不开光影时原版没有泛光，画布里要烘焙一层柔和光晕，发光感才够。
   - 开光影时光影包自带泛光，烘焙光晕按配置 `shaderPackGlow`（默认 0.6）缩小，避免过曝。
   - 是否在用光影包，每帧通过 Iris API 的 `isShaderPackInUse` 查询，玩家随时切换光影都能跟上。
4. **材质集中定义在一处**，光影实测后可以整体替换：

   | 部件 | 首选材质 | 混合 | 光影下对应程序 | 备选 |
   | --- | --- | --- | --- | --- |
   | 法阵、冲击波、抵达符印、能量流、光柱 | `RenderType.eyes(画布)` | 叠加，不写深度 | `gbuffers_spidereyes`，多数光影按自发光处理 | `RenderType.beaconBeam(画布, true)`，对应 `gbuffers_beaconbeam` |
   | 符文光幕 | `RenderType.entityTranslucentEmissive(画布)`，与圣剑光效相同 | 半透明 | `gbuffers_entities` | 同上 |

5. **失败保护**：着色器编译失败、画布创建失败或屏幕效果出错时，记一次日志，只关闭对应的层；原版粒子和音效照常，不会崩溃，也不会黑屏。
6. **资源重载**：重载资源或切换光影后，着色器重新编译、画布重建；窗口尺寸变化时，屏幕效果用的拷贝缓冲随之重建。

### 3.3 不采用的做法

- **检测到光影就不画着色器层**：开光影的玩家完全看不到新效果，不符合要求。
- **把图案预先画成静态贴图**：光影兼容，但描线、闪烁、脉动这些逐帧变化只能靠拼面片近似，动画生硬。逐帧烘焙画布能保留完整的程序化动画，代价只是每帧多几次小尺寸离屏绘制，开销见 6.5。
- **借用原版后处理槽（`GameRenderer.loadEffect`）**：会和旁观者视角的生物滤镜等原版效果互相顶掉。

## 4. 视觉设计

### 4.1 部件

| 部件 | 形态 | 位置与尺寸 | 动画要点 |
| --- | --- | --- | --- |
| L1 地面法阵 | 多层同心圆、符文带、星形连线、刻度环、节点小圆、中心印记，底下一层柔和光池 | 召唤半径 5 格，图案从半径 1.6 起（3×3 以内被结构挡住）；传送半径 3.5 格，3×3 地板在内 | 线条按进度逐条"描"出来，笔头最亮；符文带内外反向旋转；每段蓄能时全阵脉冲一次 |
| L2 符文光幕 | 围绕结构的一圈半透明圆筒，符文分 3 行缓慢上行，底亮顶淡 | 召唤半径 2.4、最高 3.5 格；传送半径 2.0、最高 2.8 格 | 从地面升起；视线掠过的侧缘更亮，有体积感 |
| L3 能量流 | 外围方块各引出一道弧形光带汇入核心，亮点沿光带流向核心 | 召唤：顶层十字 4 块和中层 4 角；传送：地板外圈 8 块 | 逐道依次点亮，越接近释放越快、越亮 |
| L4 核心光柱 | 面向镜头的柱状光，中心白热、外层主题色，内部纹理向上流动 | 召唤从结构顶部（核心上方 2 格）起，传送从核心方块顶部起；高度 1→2→3 格 | 跟三段蓄能同步长高；最后 10 tick 呼吸式脉动 |
| L5 召唤释放 | 通天光柱、地面冲击波环 | 光柱高 96 格，160 格内可见；冲击波半径从 1.5 扩到 12 格 | 光柱 3 tick 冲天，30 tick 内收细消失；冲击波 14 tick 内扩散变淡 |
| L6 抵达符印 | 简化法阵，加一道下落的光柱 | 半径 2.5 格，贴合返回平台 | 一出现就全亮，30 tick 内旋转淡出；光柱从 6 格高落到地面 |
| L7 屏幕效果 | 传送旋涡（扭曲、拉伸、主题色暗角、色差、末尾白闪）、抵达闪光淡出、召唤涟漪（折射环） | 旋涡和抵达闪光只给发起者；涟漪给 32 格内能看到核心的玩家，强度随距离衰减 | 见 4.3 |

法阵贴合地形：

- 以核心为中心逐格找地面：在核心高度上下几格内，取顶面是完整实心面、上方没有遮挡的方块，在地面上方 0.015 格处画一块面片。
- 图案按世界水平坐标计算，所以台阶上下两块面片的花纹是连续的。断崖和悬空的格子直接不画，不会出现悬空的光圈。
- 召唤结构占用的 3×3 不画，那里被方块挡住；传送的 3×3 地板要画，只有核心方块那一格不画。
- 水和熔岩不算地面，会继续向下找。

基岩破坏者没有蓄能和结构，按"连敲三下"的节奏接入，主题 `bedrock`（灰 → 橙红）：

## 5. 服务端与脚本

### 5.1 数据流

```text
KubeJS 服务端（spawn_struct_base.js 的各时间点）
  → RitualFx.visual.*（ritual_fx.js 里的桥接）
  → 特供模组 RitualVisuals（服务端接口）
  → RitualVisualPacket（每个阶段一个包）
  → 范围内的客户端 RitualVisualClient
       ├ 每帧开头：烘焙画布（自写着色器）
       ├ AFTER_PARTICLES：用原版材质画世界几何
       └ renderLevel 返回后：屏幕效果
```

### 5.2 网络包 `RitualVisualPacket`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| dimension | 资源位置 | 客户端只接受当前维度的包 |
| id | long | 核心方块坐标（`BlockPos.asLong`），同一处仪式的各阶段靠它关联 |
| stage | 枚举 | CHARGE、INTERRUPT、RELEASE、WARP、ARRIVAL |
| kind | 枚举 | SUMMON、PORTAL、BREACH（基岩破坏者） |
| style | 字符串，不超过 32 字符 | 主题名；客户端不认识时用默认样式 |
| colorA、colorB | int（RGB） | 主题主色、辅色 |
| x、y、z | double | 核心中心或抵达点 |
| duration | varint | 蓄能或旋涡时长（tick） |
| entity | varint | 发起者实体 ID，没有时为 -1 |
| param | float | 按 kind 解释：地图传送是罗盘指向（度），基岩破坏者是第几下（1–3），没有时为 NaN |

- **大小**：每个包约 70 字节。一次仪式最多 4 个包（蓄能、旋涡、释放、抵达），比现在逐 tick 发的粒子命令少得多。
- **发送范围**：
  - CHARGE、INTERRUPT、RELEASE：同维度、核心 96 格内的玩家；
  - WARP：只发给发起者；
  - ARRIVAL：抵达点 96 格内的玩家，包括刚到的发起者。
- **中途进入范围**：蓄能中途走进范围的玩家看不到这一次的着色器层（蓄能只有 2 秒，可以接受），原版粒子照常可见。
- **时序**：客户端以收到包的时刻为起点，释放和中断以收到的包为准。超过蓄能时长 40 tick 还没收到下一个包时自动淡出。
- **协议号**：新增包后，特供模组网络协议号 7 → 8。旧客户端进不了新服务端，会提示版本不符；特供模组本来就要求两端同版本。

### 5.3 服务端接口 `RitualVisuals`

给 KubeJS 调用。全部是静态方法，参数只用基本类型和字符串，不重载（KubeJS 对重载方法的解析不可靠，曾在 `distanceToSqr`、`moveTo` 上出过错）：

```java
boolean charge(Level level, int x, int y, int z, String kind, String style, String colorA, String colorB, int ticks, double param)
boolean interrupt(Level level, int x, int y, int z)
boolean release(Level level, int x, int y, int z, String kind, String style, String colorA, String colorB, int travelerId)
boolean warp(ServerPlayer player, String kind, String style, String colorA, String colorB, int ticks)
boolean arrival(Level level, double x, double y, double z, String kind, String style, String colorA, String colorB, int travelerId)
```

- `colorA`、`colorB` 直接用主题里的尘埃色字符串，例如 `'0.35 0.9 0.85'`。
- 返回 false 表示没有发出（参数无效、在客户端调用等），脚本据此退回原版表现。

## 6. 客户端实现

### 6.1 类

| 类 | 作用 |
| --- | --- |
| `client/ritual/RitualVisualClient` | 接收包，维护进行中的仪式（最多 8 个），按阶段推进；在 `AFTER_PARTICLES` 画世界几何；切换世界时清空 |
| `client/ritual/RitualGeometry` | 收到 CHARGE 时一次性采样地面，生成法阵面片；每帧更新光柱和能量流朝向镜头的面片，复用数组，不分配新对象 |
| `client/ritual/RitualCanvas` | 离屏画布：帧缓冲加颜色纹理，以 `ResourceLocation` 注册进纹理管理器，供原版材质引用；按池复用 |
| `client/ritual/RitualBaker` | 每帧开头把各画布烘焙成当前帧的图案 |
| `client/ritual/RitualScreenEffect` | 屏幕效果：拷贝主帧缓冲，再画一遍全屏 |
| `client/ritual/RitualShaders` | 在 `RegisterShadersEvent` 注册 4 个着色器；失败时关闭对应的层 |
| `client/ritual/IrisCompat` | 查询 `isShaderPackInUse`。解析方式同 `IrisShadowPass`：只解析一次，绑定 MethodHandle，没装 Oculus 时返回 false |
| `mixin/client/GameRendererRitualScreenMixin` | 在 `GameRenderer.render` 里 `renderLevel` 返回后调用屏幕效果 |

### 6.2 画布

| 画布 | 尺寸 | 内容 |
| --- | --- | --- |
| 法阵 | 1024×1024，32 格外降到 512 | 法阵、光池、抵达符印 |
| 冲击波 | 512×512 | 释放时的冲击波环 |
| 光幕 | 1024×256 | 横向绕一圈 360°，3 行符文 |
| 光柱 | 64×512 | 光柱截面和向上流动的纹理 |
| 能量流 | 256×32 | 光带截面和流动亮点 |

- 同时最多给最近的 3 个仪式分配完整画布，每套约 6 MiB 显存；更远的只画光柱。
- 烘焙频率：48 格内、在视野里的仪式每帧烘焙；更远的每 3 帧一次；看不见的不烘焙。
- 烘焙在世界绘制之前进行，前后保存并恢复帧缓冲绑定和视口。

### 6.3 着色器

| 着色器 | 用途 | 主要 uniform |
| --- | --- | --- |
| `ritual_circle` | 法阵、冲击波、抵达符印、基岩裂隙，用 `Mode` 区分 | `Time`、`Progress`、`Phase`、`PhaseTime`、`Style`、`ColorA`、`ColorB`、`Heading`、`Glow`、`Detail` |
| `ritual_runes` | 符文光幕 | `Time`、`Progress`、`Style`、`ColorA`、`ColorB`、`Glow` |
| `ritual_beam` | 光柱、能量流的截面 | `Time`、`Intensity`、`Style`、`ColorA`、`ColorB`、`Glow` |
| `ritual_screen` | 屏幕效果 | `Mode`、`Strength`、`Center`、`Radius`、`Tint`、`Time` |

- 共用函数放在 `shaders/include/ritual_common.glsl`：
  - 哈希噪声、线段距离、星形多边形、光晕衰减；
  - 程序化符文：在 3×4 点阵中按哈希取 3–5 条线段。
- 法阵里每个元素有自己的出现区间（按 `Progress`）。描线用沿圆周或沿线段推进的遮罩，笔头加一点高亮。
- 雾、距离淡出和光影效果都交给世界材质，烘焙着色器只负责图案本身。

### 6.4 屏幕效果

- 只在有效果时运行，平时零开销。
- 流程：用 `glBlitFramebuffer` 把主帧缓冲的颜色拷进一个同尺寸缓冲（窗口尺寸变化时重建），再画一个全屏三角形，采样拷贝、写回主帧缓冲。
- **旋涡**：绕屏幕中心旋转扭曲，加径向拉伸；色差随半径增大；主题色暗角；末段叠加白闪。
- **召唤涟漪**：把核心投影到屏幕上，以它为圆心扩散一圈折射环，环上带轻微色差。核心在身后时不做。
- 强度受客户端配置 `intensity` 影响；`screenEffects=false` 时整段跳过。

### 6.5 性能预算

| 项目 | 上限 |
| --- | --- |
| 世界绘制 | 每个仪式最多 5 次绘制调用，约 2500 个顶点；冲击波阶段约 3500 |
| 烘焙 | 每个仪式每帧最多 5 次离屏绘制，总像素约 160 万；远处减到四分之一 |
| 屏幕效果 | 一次全屏拷贝加一次全屏绘制；每次仪式最多持续约 1.75 秒 |
| CPU | 地面采样只在收到 CHARGE 时做一次，最多约 100 格；每帧不分配对象 |
| 网络 | 每次仪式最多 4 个包，每个约 70 字节 |

实装后在主整合包用 spark 对比仪式期间的帧时间，普通和光影各测一次。

### 6.6 客户端配置

加在特供模组现有配置文件的 `ritualVisuals` 段：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | true | 着色器层总开关 |
| `screenEffects` | true | 屏幕效果（旋涡、闪光、涟漪） |
| `intensity` | 1.0 | 整体亮度，0.25–1.5 |
| `shaderPackGlow` | 1.0 | 开光影时烘焙光晕的倍率，0–1（实测 Complementary 下偏暗而非过曝，默认改为 1.0） |
| `maxDistance` | 128 | 世界几何的最远绘制距离，32–256；通天光柱固定 160 格 |
| `canvasResolution` | 1024 | 法阵画布边长：512、1024 或 2048 |

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 某个光影包对 `gbuffers_spidereyes` 处理特殊，比如不发光或混合方式不同 | 材质集中在一处，实测后整体换成 `beaconBeam` 备选 |
| 极佳（Fabulous）画质下半透明层的顺序 | 与圣剑、金十字光效在同一绘制阶段；按验证矩阵确认 |
| 烘焙时改了帧缓冲或视口却没恢复 | 烘焙前后保存、恢复；每次都在世界绘制之前进行 |
| 屏幕效果和其他后处理叠加（旁观者滤镜、ModernUI 模糊） | 挂在 `renderLevel` 之后、原版后处理和界面之前；ModernUI 的模糊在界面阶段，不冲突 |
| 资源重载或切换光影后着色器丢失 | 重载时重新注册、重建画布；失败只关闭着色器层 |
| 网络延迟 | 阶段以收到的包为准，客户端有超时淡出，不会卡在半途 |
| ImmediatelyFast 的缓冲批处理 | 用独立的固定缓冲源，同金十字光效的做法 |
