# 新区块生成与载图性能调查

调查日期为 2026-11-07。用户反馈单人游戏和多人服务器均有明显问题。

后续固定种子的主世界对照测试已定位到 Tectonic 与 AE2 陨石高度查询的组合热点，结果见[主世界对照测试](C:/Users/Tony/AppData/Roaming/PrismLauncher/instances/SenDimsBanForges/minecraft/docs/development/SDBF-主世界地形群系与结构对照测试-2026-11-07.md)。下文记录初查过程。资源定义数量已按实际 JSON 文件复核，排除了初版统计混入的目录项。

## 结论与证据范围

本次读取本机日志、367 个 JAR 的世界生成资源、KubeJS 数据覆盖、三个本地存档的生成器配置，以及日志中已有的 Spark 原始采样。成功取回一份 15.141 秒的服务端采样和一份 60.018 秒的客户端采样，另一份实时采样链接已经返回 404。

现有采样明确暴露了星界装备每 tick 重算、深四运行时地形查询、飞行生物寻路和客户端渲染的负担。两份采样都只记录了一条主线程，缺少世界生成工作线程，主世界各个生成模组的实际耗时排名仍需补充测量。下文将实测归因和配置、代码分析得到的测试优先级分别说明。

## 已有服务端采样

采样服务器运行 Forge 47.4.20、Java 21.0.2、DeepRealm 0.1.9，JVM 可见 8 个逻辑处理器，采样结束时有 3 名玩家。已加载实体分布包括主世界、深四、深二、豆腐世界等维度。

结束时最近一分钟 TPS 约 10.35，MSPT 平均约 93.37 ms，中位数约 71.90 ms，P95 约 137.97 ms。该窗口已经存在明显的主线程压力。[原始服务端采样](https://spark.lucko.me/MPXI35D2E0)

| 调用范围 | 服务端主线程样本时间 | 主线程样本占比 |
| --- | ---: | ---: |
| 星界装备 `AstralScoreEngine.calculateEquipped` | 4408 ms | 29.43% |
| 自然刷怪 `NaturalSpawner` | 2592 ms | 17.31% |
| 生物寻路器 | 1924 ms | 12.85% |
| 深四 `worldgen` 包下的运行时查询 | 1336 ms | 8.92% |
| Terra Entity 的 Pixie 实体 tick | 1176 ms | 7.85% |
| Bumblezone 丝帘实体判断 | 572 ms | 3.82% |

每行采用该调用范围的子树并集，消除递归、嵌套调用导致的重复累计。不同行会互相包含，例如 Pixie 包含部分寻路，刷怪包含部分深四地形查询。表中比例均以这一条线程的 14976 ms 样本时间为分母，不宜相加或理解成整个 JVM 的 CPU 占比。

### 星界装备计算

已核对安装的 JAR 字节码。`AstralContainerItem.curioTick` 每次都会调用 `AstralCurioAttributes.refresh`，后者无条件读取容器并执行 `calculateEquipped`。属性和分数快照只减少最终写回次数，完整计算仍然发生。调用栈内出现大量 Rhino 数值包装、解释器和节点依赖计算。

优先改为按输入变化失效的缓存。缓存应覆盖容器布局、填充物数据与版本、同组饰品互斥关系、读取的玩家状态、维度、时间及其他动态依赖。静态节点、已解析的数值和依赖图可复用，动态条件发生变化时再重算。重算边界必须跟实际规则一致，白天夜晚、受伤状态和装备变动等条件仍需及时更新。

这是现有证据中保留玩法、减少重复计算收益最明确的一项。29.43% 是本次采样中的占比，优化后的整服收益尚未测量。

### 深四地形与刷怪查询

实际调用链包括自然刷怪检查进入 `SpiralChunkGenerator.getBaseHeight`，再进入 `TerrainProfile.sample`。因此地形计算也会出现在已经生成的区块中。安装版本已经有线程局部缓存和区块快照，可以进一步核查刷怪查询的命中率、缓存碰撞及快照复用。

可将只依赖种子、生成版本和水平坐标的纯地形结果缓存到有界的区块列数据中。查询生成器理论高度时保持原算法语义，查询现存区块实际表面时使用相应高度图。两个查询口径需要分别验证。

### 寻路与蜜蜂领域回调

飞行寻路约占主线程样本的 12.85%。Bumblezone 的 `StringCurtain.shouldBlockOffEntity` 约占 3.82%，它通过全局飞行寻路注入参与工作。

安装版本的 `getCurtainBlockPathType` 在检查目标方块是否属于丝帘标签之前，先做实体判断。可评估在实际丝帘方块上执行完整逻辑，并缓存适用范围正确的实体判定。应验证蜂类、相关实体标签、装备或效果变化对结果的影响。此项有具体热区，适合定点补丁。

## 主世界新区块生成的重点对象

主世界当前采用噪声生成器。本地存档的主世界多噪声群系源保存了 1705 条气候映射条目。该数值指映射条目数量。Tectonic 配置的垂直范围为 -64 到 320，`ultrasmooth` 关闭，主要洞穴类型、地下河等选项开启。

| 对象 | 已检查到的内容 | 预计主要影响与验证方法 |
| --- | --- | --- |
| Tectonic 与 Terralith 组合 | Tectonic 启用，包含 Terratonic 兼容覆盖。Terralith JAR 内有 134 个群系、104 个密度函数、570 个放置地物定义 | 持续的新区块噪声、地表与装饰成本。固定种子分组停用，比较 noise、surface、features 阶段 |
| Regions Unexplored | JAR 内有 71 个群系、343 个放置地物定义，配置中各类群系开启 | 部分群系的树林、洞穴装饰及表面规则，观察慢区块对应群系 |
| Dungeons Arise | 819 个结构模板，39 个结构定义，其中存在超大单模板 | 更值得优先检查遭遇结构时的尖峰，先针对 `keep_kayra` 单独做 A/B |
| ATi Structures | 72 个模板、55 个结构定义，多个大模板 | 结构密集区和大型建筑的放置尖峰，可作为较低整合依赖的删减实验 |
| Darker Depths、YUNG's Cave Biomes、Biome Makeover、Quark | 地下群系、地物与自定义生成代码同时存在，Quark 多项世界生成开关开启 | 检查 features、carvers 和 surface 的具体堆栈后再决定取舍 |

这些定义数量用于说明检查范围，实际每个区块只使用适用群系和放置规则，数量本身不能换算成耗时或性能排名。

### Dungeons Arise 的巨大模板

已直接解码 `data/dungeons_arise/structures/keep_kayra/keep_kayra_main_0.nbt`。

| 数据 | 数值 |
| --- | ---: |
| 尺寸 | 163 × 250 × 163 |
| 方块信息记录 | 1,236,233 |
| 其中空气记录 | 291,530 |
| 模板实体记录 | 44 |
| 解压后的 NBT | 44,847,952 字节 |

对照读取的 ATi `steam_house` 模板为 110329 条方块记录，尺寸 48³。前者单个模板的记录规模约为其 11 倍。

1.20.1 的基础结构放置路径会处理模板方块列表、转换坐标、运行处理器并执行边界内的放置，巨型模板因此具有明显的尖峰风险。现有 Lithostitched 的 `StructureTemplateMixin` 负责绑定处理器，其功能不包含对这些记录做空间裁剪索引。具体尖峰时间和其他注入的影响仍需要运行时测量。

当前整合包的 Dungeons Arise 大型结构间距为 60、小型结构间距为 35，和这个已安装版本内置值一致。先停用或单独稀疏化 `keep_kayra`，可以在保留其他建筑的情况下检验其影响。若将大型结构组间距从 60 改为 80，在其他条件相同时，候选格点密度约减少 43.75%。实际成功生成数量和耗时还取决于群系及放置条件。

进一步保留外观的代码优化方向是按空间索引模板块、避免重复扫描整个巨型列表。结构处理器可能使用随机数、移动位置或读取全局列表，优化需要验证生成结果、实体、箱子战利品、流体、旋转和区块边界，不能直接把所有模板统一截断。

## 客户端载图与渲染

客户端采样只包含 Render thread，共 60.018 秒。该采样中方块实体渲染子树约占 26.33%，光影阴影约占 13.04%，两者存在嵌套。调用栈还包含 Integrated Dynamics 的轮廓形状、YSM、拔刀剑模型、Accelerated Rendering 和 OpenGL 驱动调用。[原始客户端采样](https://spark.lucko.me/SngPCxgcO8)

该采样结束时集成服务器最近一分钟 MSPT 平均约 3.55 ms，TPS 约 20，说明当时主要采到的是客户端渲染场景。它没有记录客户端区块网格构建工作线程，无法据此评价新区块网格构建速度。

当前磁盘上的 Oculus 配置已关闭光影，和这份历史采样的场景不同。复测应明确记录光影开关。现有视距为 16，模拟距离为 8。可以用视距 10 或 12 做探索对照，同时记录区块就绪延迟和帧时间 P95/P99，区分生成完成、网络到达与实际显示的时间。

## 保留内容的优化顺序

1. **修复重复计算。** 先处理实测约 29% 的星界装备重算，再处理深四刷怪高度查询和丝帘寻路回调。它们减少主线程争用，有利于服务器在探索时继续正常 tick。
2. **使用已安装的 Chunky 预生成重点探索区域。** 在空闲时生成主世界及常去维度，进入这些区域时就能读取已有区块。它将工作提前完成，区域以外的首次生成仍需原有计算。[Chunky 官方说明](https://github.com/pop4959/Chunky/wiki/Pregeneration)
3. **对巨型结构分别治理。** 优先测试 `keep_kayra`，其次测试 ATi 大型结构。可以降低特定结构频率、保留其余内容，或对确认存在重复扫描的路径做兼容性补丁。
4. **分别调整服务器与客户端线程预算。** 本机 Smooth Boot 主工作线程配置为 27，而本机有 24 个逻辑处理器，采样服务器 JVM 只可见 8 个。服务端应先核对实际部署值，按可用 CPU 为主线程、生成、I/O 和 GC 分配预算。客户端需给渲染和网格工作线程留出余量，具体线程数做 A/B 确定。
5. **按需启用现有 ServerCore 功能。** 当前 `reduce-sync-loads` 和 `cache-ticking-chunks` 开启，动态调节和实体激活范围关闭。实体激活范围能减少远处 AI 工作，需要按首领、农场等玩法配置排除和距离。动态视距用于过载时缓冲。以上措施主要改善运行负担，其收益需与生成阶段吞吐分开评估。

包内已经安装 Fast Noise、Starlight、Radium、ModernFix、FerriteCore、Lithostitched 等。Fast Noise 的两个现有优化开关均开启，其原理主要包括世界生成期间的块、群系数据写入与内存分配优化。针对剩余噪声计算和巨型结构工作，仍需进一步采样定位。[Fast Noise 作者说明](https://modrinth.com/mod/zfastnoise)

多线程区块生成还有独立实验空间。核验时 FastChunkGen 的 README 要求 Forge 至少 47.4.22，本机为 47.4.10、采样服务器为 47.4.20。若尝试该方向，应在独立副本统一版本并验证自定义生成器、地物线程安全、持久化与关服重开结果。该项目在本包的兼容性和收益尚未实测。[FastChunkGen 项目说明](https://github.com/shuttheirprayer/FastChunkGen)

## 若考虑删减

| 目标 | 优先候选 | 整合包影响 |
| --- | --- | --- |
| 遭遇大型建筑时的尖峰 | 先禁用 `keep_kayra`，再测试 Dungeons Arise 的大型结构组 | 保留 JAR 和注册内容可减少适配工作。整个模组涉及现有羽毛笔配方、战利品和其他维度结构引用 |
| 较低整合依赖的结构删减 | ATi Structures | 本次扫描 KubeJS 脚本、数据和 FTB 任务未发现其命名空间引用，仍需建副本验证运行结果 |
| 普通区域持续生成偏慢 | 先 A/B 停用 Tectonic，观察保留 Terralith、RU 后的差异 | 改变未来新区块地形。更换生成组合需要检查与既有区域的衔接 |
| 大幅减少群系与植被内容 | Terralith 或 RU | 需要按实际噪声、地物热点选择。RU 已被深一维度、表面规则、材料和交易引用，删除适配成本更高 |

ATi 的低耦合程度不代表已证明它的耗时高于其他结构模组。Dungeons Arise 的巨型模板也不能代表其每一种小结构都同样昂贵。当前最适合按目标进行有控制的删减试验。

## 补齐主世界耗时排名

服务端执行以下采样，覆盖生成、I/O 和主线程。分别采集静止、沿已生成路线移动、沿新区块路线移动三组，固定移动方式和路线长度。

```text
/spark profiler start --thread * --timeout 120
```

客户端同步或分次进行对应采样。

```text
/sparkc profiler start --thread * --timeout 120
```

比较 Worker-Main、Server thread、I/O 和区块网格线程，识别 `NoiseBasedChunkGenerator`、密度函数、`SurfaceRules`、`Feature.place`、`StructureTemplate.processBlockInfos`、地物所属包、光照、NBT、网格构建等调用链。必要时用 JFR 的 ChunkGeneration 事件区分生成阶段。异步任务的持续时间包含等待，不能把所有阶段持续时间相加当作 CPU 时间。[Spark 官方命令说明](https://spark.lucko.me/docs/Command-Usage)

模组 A/B 使用同种子的独立新世界，测试多块固定区域并重复运行，保持 Java、线程数、其他配置和测量方法一致。记录区块吞吐、请求 P95、最长停顿、MSPT、GC 和客户端帧时间。单人模式另外比较有玩家实体活动与纯预生成两种场景。

本次尚未执行主世界同种子 A/B 生成基准，因此暂不提供删模组后的百分比加速承诺。
