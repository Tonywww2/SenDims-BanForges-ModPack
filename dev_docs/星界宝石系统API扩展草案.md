# 星界宝石系统 API 扩展草案

> 2026-10-02 更新：84个主修饰机制现已全部确认，API扩展已由模组实现。本文保留开发前的接口建议作为设计记录；实际方法签名与行为以模组工程的《星界宝石系统-API扩展开发者指南.md》为准。当前数值草案与实装状态分别见同目录《星界宝石系统-首轮数值草案.md》和《星界宝石系统-实装与测试说明.md》。下文的历史“待审／尚未实现”状态不代表当前审批或实现状态。

本草案供星界躯体模组开发者与整合包脚本作者审阅。目标是让所有宝石填充物共用一个物品类、一个物品 ID，通过每个物品栈的 NBT 决定宝石种类、主修饰、三维、附加修饰、基础分、读取来源、最终分数及徽章转换。

本文依据当前读取到的星界躯体源码和已经讨论的宝石规则编写。所有新增接口、字段名和物品 ID 示例均为拟议内容，尚未实现。主修饰统一改为希腊字母；共用填充物物品 ID 的要求已确认。此前 15 种宝石的 37 个核心机制已确认，剩余 19 种的 47 个核心机制仍为待审草案，名称调整不等于批准这些待审机制。

## 设计范围与基本约束

- 全部 34 种宝石共用一种宝石填充物物品。每个容器格对应独立计算实例，物品 ID 相同也必须分别结算。
- 宝石加工时，将源宝石的种类与随机数据转存至填充物 NBT。已有三维、主修饰和附加修饰应完整保留，正常加工不重掷。
- 每颗宝石有一个主修饰，决定核心玩法；附加修饰只直接修改三维。品质主要让机制效率接近潜力。
- 填充物只修改自己的结果。读取来源使用副本；多个读取者可以独立取得同一个来源的完整结果。
- 读取链使用本轮已计算的结果。每轮从物品数据重新计算，分数不累加上一轮结果。
- 专属徽章只有一个宝石镶嵌位，每名玩家只能有一枚专属徽章产生效果。默认徽章的效果和获取入口需要移除。
- 徽章是最终属性转换器。分数与徽章品质效率分别压缩后组合，攻击型收益目标约为 5% → 35% → 50%，理论极限和完整条件收益可以超过 50%。
- 条件使用当前可读取的玩家或世界状态。实际属性包括已经生效的专属徽章加成。
- 六类分数为力量、敏捷、智力、体质、感知、魔力。分数自身不直接修改玩家属性。
- 共用填充物 ID、专属徽章 ID、加工材料、配方、强化成本与限制尚未确定。本文示例使用 `sdbf:gem_filler` 和 `sdbf:gem_badge`，仅作为占位。

## 主修饰的希腊字母规则

每种宝石的主修饰按原草案顺序分别标记为 α、β、γ、δ。字母在宝石种类内部区分核心，不能单独作为全局身份。不同宝石的 α 可以属于不同角色并采用不同公式。

| 显示字母 | NBT 稳定值 | 顺序 |
| --- | --- | --- |
| α | `alpha` | 第一项 |
| β | `beta` | 第二项 |
| γ | `gamma` | 第三项 |
| δ | `delta` | 第四项 |

显示名称建议为“红宝石填充物 α”等。程序使用 `source_item + primary` 查找规则，例如 `thermal:ruby#alpha`。通用 API 的逻辑规则键可采用 `sdbf:gem/thermal/ruby/alpha`。本轮删除主修饰的原具体命名，本文的玩法表和来源名单全部使用“宝石名称＋字母”。

NBT 读取工具可接受希腊字母作为输入别名，规范写出时使用 `alpha/beta/gamma/delta`；界面显示希腊字母。后续新增或删除核心不得自动重排已有字母，需要通过数据版本明确迁移。

## 当前源码能够提供的能力与缺口

| 位置 | 当前能力 | 本设计需要补充的能力 |
| --- | --- | --- |
| `AstralFillers` | 按物品 ID 注册一次固定定义，`find(ItemStack)` 只取实际物品 ID | 一个注册入口按每个物品栈的 NBT 解析逻辑种类、主修饰和规则 |
| `FillerDefinition` | `base(type, amount)` 是固定注册值；`bonus/conversion/medal` 有回调 | 由 NBT 生成动态基础分，独立节点回调，声明来源依赖，读取逐颗结果 |
| `FillerContext` | 物品副本、位置、布局、有效物品数量 | 物理占用与生效状态分离、逻辑过滤、空间查询、基础与最终结果查询 |
| `AstralScoreEngine` | 全局基础分、共享附加分快照、按格序消耗全局分数转换 | 本地读取副本、来源先于读取者结算、每格保留 B/F/Δ 和六分数 |
| `FillerActivation` 及容器插入规则 | 唯一效果与唯一佩戴按实际物品 ID 判断 | 共用填充物使用 STACKABLE；徽章另有玩家范围的效果唯一组 |
| `ScoreSheet` | 六项 double，拒绝非有限值 | 新节点模式的大数运算、稳定对数转换和可序列化显示 |
| `AstralStoredItems` | 存储完整物品栈，单格数量为一 | 沿用完整数据保存；新 payload 在存取、同步、加工后完整保留 |
| `AstralCurioAttributes` | 服务端刷新，容器上缓存总分与属性 | 动态输入失效检测、逐格摘要、全轮玩家状态、重入处理 |
| 组合锻造与投影组合配方 | 支持固定产物数据及完整 NBT 的精确原料 | 动态源数据读取、数据匹配谓词、由输入数据生成输出的加工钩子 |
| `AstralKubeJSPlugin` | 当前绑定仅提供给 STARTUP | 新注册接口仍在 STARTUP；运行时数据与加工工具同时提供 SERVER 绑定 |

不能通过为同一填充物 ID 注册 84 个定义实现本设计。正确方向是只注册一次，再对每个实际物品栈解析实例数据。计算结果、激活、读取和缓存都不能只按共用物品 ID 或规则键归并。

## 物品数据协议

### 规范数据结构

建议使用一个规范 `GemPayload` 承载原宝石、填充物和徽章中的宝石数据。Forge 1.20.1 保存为 NBT；NeoForge 1.21.1 保存为适配层对应的自定义数据组件。对脚本暴露相同的读取结果。

字段及其名称是本草案的建议：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `schema` | 整数 | payload 数据版本 |
| `source_item` | 命名空间物品 ID | 原始宝石种类，必须是 34 种允许的来源之一 |
| `primary` | 字符串枚举 | `alpha/beta/gamma/delta`，须属于对应宝石的有效主修饰 |
| `natural.size` | 小数 | 天然大小，范围 1–500 |
| `natural.purity` | 小数 | 天然纯度，范围 1–200 |
| `natural.polish` | 小数 | 天然抛光，范围 1–100 |
| `affixes` | compound 列表 | 当前保留的自然附加修饰；允许重复 |
| `reinforcements` | compound 列表 | 预留给强化造成的数值修正，具体强化机制待设计 |
| `extensions` | compound | 可选扩展数据；不作为未声明规则的自动倍率 |

每条附加修饰至少包含 `stat`、`operation`、`value`。`stat` 为 `size/purity/polish`；`operation` 为 `flat/percent`；`value` 保留正负号。百分比使用比例值，`0.25` 表示 +25%。

角色、基础分、转换倍率、来源名单、徽章属性映射及有效三维由数据与规则表推导，不作为玩家物品中的权威配置。逐颗最终分数也不是输入数据，不能从上一次预览缓存恢复成下一轮产分。

### 填充物 NBT 示例

示例中的宝石数据仅用于说明字段，不指定实际掉落或配方。

```json
{
  "sdbf.gem_filler": {
    "schema": 1,
    "source_item": "thermal:ruby",
    "primary": "alpha",
    "natural": {
      "size": 386.12,
      "purity": 127.45,
      "polish": 68.32
    },
    "affixes": [
      {"stat": "purity", "operation": "flat", "value": 18.50},
      {"stat": "polish", "operation": "percent", "value": 0.16},
      {"stat": "size", "operation": "percent", "value": -0.07}
    ],
    "reinforcements": [],
    "extensions": {}
  }
}
```

共用填充物的实际 ID 对上述 `source_item` 没有替代作用。原宝石 ID 必须保存，否则变为共用填充物后无法区分种类。

建议原宝石的新数据格式与填充物共用上述 payload 内容。原宝石的种类可以从实际物品 ID取得，加工后必须明确写入 `source_item`。专属徽章可在 `sdbf.gem_badge.gem` 中保存同一 payload 的独立副本，空镶嵌位没有该字段。

### 三维与附加修饰

三维天然值分别随机生成，保留两位小数。有效值按下式从天然值和当前保留的数值修正重算：

```text
effectiveStat = max(1, (naturalStat + sumFlat) * (1 + sumPercent))
```

百分比修饰求和后统一应用，重复修饰分别参与计算。修正后允许超过天然上限。清除负面修饰后从天然值重算，不能反复在已经修正的结果上乘除。

自然附加修饰的单条数值极限：

| 修饰 | 正面极限 | 负面极限 |
| --- | --- | --- |
| 大小固定值 | +50 | −25 |
| 纯度固定值 | +20 | −10 |
| 抛光固定值 | +10 | −5 |
| 任意三维百分比 | +25% | −12.5% |

每颗有 1–5 个自然附加修饰，主修饰不占这些位置。修饰数初始模拟权重为 15%、25%、35%、20%、5%；单条为负面的概率为 20%；幅度独立连续随机，居中常见、极端罕见。具体概率密度函数尚未校准。强化条目与自然附加修饰应可区分，供统计与未来规则使用；强化限制仍未制定。

### 品质与实际计算

三维归一化使用 `size/500`、`purity/200`、`polish/100`。填充物和徽章各自按本核心指定主三维使用 70%/15%/15% 权重。实际效果使用修正后的三维。

掉落总体质量的统计使用天然三维和自然正修饰数量：

```text
triQuality = 0.70 * naturalMainNormalized
           + 0.15 * naturalOther1Normalized
           + 0.15 * naturalOther2Normalized

qualityForUse = 0.80 * triQuality + 0.20 * positiveNaturalAffixCount / 5
overallDropQuality = max(fillerQualityForUse, badgeQualityForUse)
```

总体分布的目标仍是多数约 40%、少量约 60%、更少约 80%，末端稀有尾部延伸至 99.99% 附近。各字段独立生成，通过模拟校准总体分布；不引入品质档位或先生成一个总品质再分配三维。幸运影响、旧数据迁移和具体分布参数仍待确定。

## 数据读写与加工接口

建议新增 `AstralItemData`，作为跨版本的数据适配工具。以下签名为接口草案：

```text
read(stack, namespaceKey) -> immutable data copy or missing
writeCopy(stack, namespaceKey, data) -> new ItemStack
removeCopy(stack, namespaceKey) -> new ItemStack
deepCopy(data) -> independent data
validate(data, schemaId) -> ValidationResult
```

读写必须保留完整 compound/list、小数、百分比和重复修饰。`writeCopy` 生成新物品栈，不修改传入对象。宝石种类、主修饰合法性和天然范围由宝石 schema 校验；通用模组接口不硬编码 34 种宝石。

需要支持至少以下三种操作：

1. **原宝石加工为填充物。** 读取实际源物品及规范随机数据，验证后生成数量为一的共用填充物，完整写入 payload。
2. **原宝石镶入专属徽章。** 将同一规范 payload 的独立副本写入徽章，保持其随机结果。
3. **调整填充物或徽章中的数据。** 清除负面修饰、强化指定项或进行未来数据迁移后，重新计算有效三维并使预览与佩戴效果失效刷新。

原宝石已有数据时不能在普通加工中调用随机生成器重新掷值。缺少新格式必要数据的物品按迁移策略处理。具体拆卸、替换镶嵌宝石的成本、返还规则和强化限制尚未确定。

### 动态产物钩子

建议增加 `AstralTransforms.register(transformId, callbacks)`，在 STARTUP 定义加工规则，供配方或服务端处理过程引用：

```text
matches(ProcessContext) -> boolean
preview(ProcessContext) -> Result<ItemStack>
produce(ProcessContext) -> Result<ProcessOutput>
```

`ProcessContext` 应提供玩家当前状态、具名匹配原料的完整物品副本、催化材料、配方 ID与阶段。无序配方应按匹配角色提供 `source("gem")`，而不是假定宝石永远处于某个输入格。

`ProcessOutput` 包含带完整数据的产物及拟议消耗、返还项。先确认输入和输出有效，再由加工系统一次性提交。失败时返回原因，原料不消耗；预览不修改物品或重掷宝石数据。物品数据应在提交时重新读取或核对，以免预览之后修改输入而得到旧数据产物。

组合锻造与投影组合需要能够引用 `data_transform`，并允许“实际物品 ID或 tag＋数据谓词”的匹配方式。普通随机宝石的三维不同，不能要求它们与配方里的一份固定完整 NBT完全相同才能加工。

动态产物也可以由服务端脚本创建。数据工具与注册工具应分开提供，避免加工必须发生在 STARTUP。具体使用哪种加工方式由后续配方设计决定。

### 旧宝石数据

目前原宝石脚本读取的是 `sdbf.gemdata` 内的 `gemScale/gemPurity/gemPolish` 整数和 `gemAffix` 字符串列表，另有 `sdbf.gem_tier`。这些旧修饰字符串没有新版单条数值，也没有希腊字母主修饰，不能唯一还原成新版数据。

必须提供版本识别和迁移入口，但旧宝石采用重新生成、映射迁移还是限定新区获取，尚未批准。本草案不自动给旧宝石补 α、不擅自根据旧字符串编造新修饰数值。加工失败信息应指出待迁移数据，而不是静默产生一种不同的宝石。


## 动态填充物注册

建议保留现有 `AstralFillers.register(itemId, definition)`，在 `FillerDefinition.Builder` 上新增 `node(resolver)`，启用逐颗节点模式。共用物品 ID 只注册一次，resolver 为每个物品栈生成独立的 `FillerNode` 描述。

| 拟新增入口 | 职责 |
| --- | --- |
| `node(instanceContext -> FillerNode)` | 读取本颗物品快照，解析其 NBT，选择对应规则 |
| `FillerNode.kindKey(key)` | 逻辑宝石种类，如 `thermal:ruby` |
| `FillerNode.variantKey(key)` | 逻辑主修饰，如 `alpha` |
| `FillerNode.ruleKey(key)` | 种类与主修饰组合后的稳定规则键 |
| `FillerNode.role(role)` | 原生、放大或转换，供逻辑过滤与显示 |
| `FillerNode.data(data)` | 本轮深复制、只读的实例数据 |
| `FillerNode.intrinsic(callback)` | 从实例数据计算基础六分数与 B |
| `FillerNode.reads(callback)` | 声明元数据、基础分或最终分数的候选来源 |
| `FillerNode.calculate(callback)` | 从本轮条件与完成的来源副本计算本颗最终分数 |
| `FillerNode.invalid(reason)` | 保存物品但不产生分数，提供明确失效原因 |

回调的输入结构必须对 Java 与 KubeJS 都可访问。resolver 每轮或输入改变后按每个栈执行，不能只按实际物品 ID、kindKey 或 ruleKey 缓存。相同种类和字母但三维不同的两颗宝石，结果必须不同；NBT 完全相同但位置不同的两颗，布局结果也可以不同。

### 注册示意

以下是拟议 API 的用法示意，不能直接用于当前版本。`GemPayload` 和 `GEM_RULES` 由宝石脚本提供，不要求模组硬编码宝石种类与数值。

```js
const COMMON_FILLER_ID = 'sdbf:gem_filler'
const PAYLOAD_KEY = 'sdbf.gem_filler'

AstralFillers.register(COMMON_FILLER_ID,
  FillerDefinition.builder()
    .activation(FillerActivation.STACKABLE)
    .node(instanceCtx => {
      const parsed = GemPayload.decode(
        AstralItemData.read(instanceCtx.filler(), PAYLOAD_KEY)
      )
      if (!parsed.ok) return FillerNode.invalid(parsed.reason)

      const data = parsed.value
      const rule = GEM_RULES[data.source_item + '#' + data.primary]
      if (!rule) return FillerNode.invalid('unknown_gem_primary')

      return FillerNode.builder()
        .kindKey(data.source_item)
        .variantKey(data.primary)
        .ruleKey(rule.key)
        .role(rule.role)
        .data(data)
        .intrinsic((instanceData, baseOut) =>
          rule.base(instanceData, baseOut))
        .reads((queryCtx, instanceData) =>
          rule.sources(queryCtx, instanceData))
        .calculate((calcCtx, instanceData, inputs, ownOut) =>
          rule.calculate(calcCtx, instanceData, inputs, ownOut))
        .build()
    })
    .build()
)
```

示例中的 GemPayload 与 GEM_RULES 必须由注册时可用的同一启动脚本作用域提供。服务端加工通过已注册 transform ID或通用数据工具调用，跨脚本阶段的数据访问需要明确接口。

规则表由 `source_item + primary` 索引。运行时改变 payload 即可切换种类、主修饰、基础分、效率、读分策略和徽章转换配置，不需要为同一个物品 ID 重新注册。修改规则代码仍遵循启动脚本的重启规则；仅修改物品数据不需要重启。

### 逻辑身份与计算身份

逻辑身份用于查找玩法。计算身份建议由“玩家／容器定位＋本轮编号＋格子索引”构成。每格都是独立节点，相同 ruleKey 也不会合并。

共用填充物使用 `STACKABLE`。建议填充物本身最大堆叠数为一；是否允许背包内同数据堆叠仍属物品设计选择，容器中每格始终保存一个完整栈。即使两个栈具有相同数据或复制出的相同 UUID，也必须按格分别结算。

## 格子视图与逻辑过滤

建议新增 `CellView`：

```text
index, x, y
inBounds
open
occupied
effective
inactiveReason
itemCopy()
actualItemId
kindKey
variantKey
ruleKey
role
instanceData
```

`occupied` 表示物理有物品；`effective` 表示本轮被选为有效计算实例。关闭格、冲突格、重复失效格和数据无效格可以 occupied=true、effective=false。不存在的格子返回明确的 inBounds=false 视图。

`ctx.cellAt(x,y)` 返回真实格子视图。现有 `itemAt` 的“只返回生效物品”语义保留，不能让新脚本误把其空结果当作物理通道。

建议增加 `FillerFilter` 的 `item/kind/variant/rule/role/where` 条件与任意条件组合。逻辑种类和主修饰必须从解析后的 NBT 实例取得。例如：

```text
item(COMMON_FILLER_ID) + kind("thermal:ruby") + variant("alpha")
role("producer") + item(COMMON_FILLER_ID)
rule("sdbf:gem/thermal/ruby/beta")
anyOfRules([...完整规则键...])
```

`count(itemId)` 仍是实际 ID 数量。需要“多少颗石英”“多少种宝石”“有没有一个放大型”的规则时，使用逻辑过滤后的格子，不能用共用填充物 ID 代替种类或角色。

## 空间查询

所有查询限定在当前容器，不跨容器取得来源结果。返回格子引用、配对或格子集合，核心再应用来源过滤。

| 拟新增辅助查询 | 语义 | 对应机制 |
| --- | --- | --- |
| `orthogonal()` | 四向相邻格 | 普通读分、空格、角色、种类统计 |
| `diagonal()` | 四个斜角相邻格 | 末影水晶 α、方氟钾石 β |
| `offset(dx,dy)` | 任意相对坐标 | 龙石 γ 的距离二格目标 |
| `opposedPairs()` | 左右、上下两组相对格 | 粗制青金石 β、振动水晶 α |
| `clockwiseNeighbors()` | 上、右、下、左的稳定环序 | 预知水晶 β |
| `mirrorCell()` | `(width−1−x, height−1−y)` | 末影水晶 β |
| `squaresContainingSelf(2)` | 最多四个包含自身的 2×2 方阵 | 方氟钾石 α、γ |
| `ray(direction, continuePredicate)` | 按距离递增的连续直线，遇截断条件停止 | 砷化硼 β |
| `connected(filter)` | 按四向连通统计匹配且生效的格子，每格只计一次 | 菱锰 α、β |

这些辅助查询可以基于 CellView 在脚本层实现；模组提供等价稳定工具可以减少重复坐标代码。连通区域统计读取位置与逻辑身份，不读取其最终分数，因此不产生数值依赖闭环。

龙石 γ 的中间格要求 open=true 且 occupied=false，目标 effective=true；原石英 α 的空格同样要求开放和物理为空。六方氮化硼 α 只计算容器网格外边界，关闭的内部格不算边界。镜像为自身时没有外部来源。

## 基础分与最终结果

建议新增只读 `FillerResult`：

```text
cellRef, kindKey, variantKey, ruleKey, role
baseScores               // 六类基础分
baseTotal                 // B
finalScores              // 六类最终分
finalTotal                // F
gainTotal                 // Δ = max(F - B, 0)
gainRatio                 // g = F > 0 ? Δ/F : 0
computed
state
diagnostics
```

B 只由本颗 NBT、有效三维及固定核心参数决定，排除布局、玩家条件和读分奖励。动态模式可以在最终计算中改变分数类型；仅切换类型而总量不变时不产生加工增量。

F 是本颗最终六分数之和。按整体加工占比分摊时，某项 X 的加工份额定义为 gX，剩余为 (1−g)X。它用于六方氮化硼 β、蓝宝石 γ 等草案，不要求追踪每一次转换的逐类型来源历史。

拟新增查询：

```text
ctx.baseAt(cell)   -> completed intrinsic scores and B
ctx.resultAt(cell) -> current-round final result or unavailable state
ctx.inputs()      -> declared source results and independent local copies
```

原石英、方阵和连片等元数据读取不需要最终结果。诱引水晶 α、方氟钾石 γ、充能红石 α 等基础分读取也不等待来源完成加工。需要最终结果时必须在读取计划中声明。

## 读取计划与节点结算

建议新增 `ReadPlan`，区分三类读取：

```text
metadata(portName, cells, filter)
baseScores(portName, cells, filter)
finalScores(portName, cells, filter)
```

`reads` 阶段可以访问完整实例元数据、玩家本轮快照和已经完成的基础分，不能依据尚未计算的最终分数选来源。先声明所有可能使用的最终来源，再由计算阶段进行最高值、最小值、正分数类型和收益比较。

finalScores 读取形成来源→读取者的边；metadata 和 baseScores 不形成最终分数依赖。对未声明的最终结果读取应报诊断，避免脚本绕过结算顺序。

建议 `Inputs` 提供完成的候选、最高/最低筛选、相对格配对，以及不同来源的组合选择。明确要求不同邻格的核心不能从同一格同时拿两个输入充数。一个混合分来源仍可按规则读取整张分数表。每个接收者对同一来源的读取是独立的。

### 每轮结算顺序

1. 获取当前容器物品和布局快照，以及本轮玩家状态。
2. 按每个物品栈的 NBT 解析实例，确定有效状态和逻辑身份。
3. 计算所有有效实例的基础分，保存 B。
4. 收集元数据／基础／最终读取计划，建立最终分数依赖图。
5. 按来源先于读取者的顺序计算，每格仅一次，生成 F、Δ、g。
6. 汇总本轮最终分数，完成效果唯一组选择。
7. 徽章读取镶嵌 payload 和最终分数，输出有限的玩家属性修饰。
8. 提交属性缓存和客户端摘要。

独立节点的并列顺序应稳定；建议沿用格子索引。出现意外闭环时，先完成无环部分，再对余下节点采用稳定格序，本轮尚未完成的来源视为不可用。保留自身基础结果并记录环及被跳过的边。这个兜底不借用旧分数，也不在一轮中反复迭代。

### 本地运算与异常

`LocalScoreWriter` 建议提供 `get/add/set/replace`，只作用于本节点，初始为基础分副本。读取副本可用 `LocalInput` 的 get/consume/split 等操作。转换不能扣减来源节点或容器全局预算。

缺少合格来源时保持本核心的弱基础分。节点 calculate 抛异常时，整次计算回退为 B，丢弃部分写入并记录原因；不可让一半转换结果提交。无法解析有效实例或无法取得合法基础分的节点不产生分数，但保留物理占用。

### 旧管线兼容建议

现有 Java 与 KubeJS 注册签名保留。只包含旧填充物的容器须与原基础／附加／转换／勋章算法一致。

混用时建议先运行旧填充物子集的旧管线，得到 L；再运行新节点，得到各自 N。新汇总分数为 `G=L+sum(N)`。旧全局转换只处理 L，旧勋章读取旧管线结果，新 `bigMedal` 读取 G。旧来源缺少逐颗最终结果时，应返回明确的 legacy/unavailable 状态；要成为新来源须显式增加节点适配。此兼容桥接是 API 实现草案，需要在开发者评审中确认。

## 玩家状态与刷新

新节点的条件应读取同一份 `PlayerStateSnapshot`。建议至少提供：

- 当前生命、最大生命、生命比例。
- 实际属性值，按完整 attribute ID 查询，包括已经生效的专属徽章属性。
- 经验等级与当前经验条进度、饥饿值。
- 当前是否落地、是否潜行。
- 主手物品是否可损坏、已损耗及剩余耐久比例。
- 当前维度、游戏时间、主世界昼夜、当前所在维度天气。
- 脚本声明使用的解锁标记或进度数据，支持“进入深四后才能使用”的条件。

原红宝石 γ 的生命模式已经确认采用围绕 30% 的平滑过渡，具体宽度待定。动态属性反馈应按真实属性快照测试，不能通过扣除本系统修饰改变已确认条件。属性查询重入须在运行时层处理，防止本次计算在取得实际属性时再次进入自身。

刷新接口建议：

```text
AstralRuntime.invalidate(player)
AstralRuntime.invalidate(player, container)
AstralRuntime.updateCell(player, container, index, transform)
AstralRuntime.recalculate(player, container)
```

updateCell 用于强化、数据迁移等服务端操作。它读取真实储存格，给 transform 一份副本，验证后完整写回物品，并标记分数及属性缓存失效。计分回调中保持只读，不能通过此接口修改当前输入。

缓存输入至少涵盖每格规范 payload、布局、装备状态、嵌入宝石、规则版本和使用的条件字段。NBT 即使在物品 ID、数量、位置都不变时改变，也必须触发重新解析与计算。缓存键必须包含格子和容器定位；数据摘要排除输出预览缓存，避免结果写回不断触发输入变化。

时间、生命及属性条件需要可配置的刷新机制。具体刷新频率尚未决定。卸下、更换、删除或禁用徽章后，应清除旧属性修饰。玩家快照与属性提交分开，防止前几个核心看到旧属性、后几个看到新属性。

## 徽章与默认勋章管理

现有 `medal` 已能通过 context 的物品副本读取 NBT，但其分数表是 double。建议新增 `bigMedal(context, BigScoreSheet, AttributeWriter)`，供共用徽章读取大数汇总，并以嵌入 payload 的种类和主修饰选择转换规则。

`AttributeWriter.add/multiplyBase/multiplyTotal` 保持有限 double 的输出形式。大数压缩发生在输出前。空镶嵌位、非法嵌入数据和失效徽章不输出属性修饰。

建议新增效果唯一组：

```text
effectGroup(groupKey, scope)
scope = CONTAINER | PLAYER
```

本系统的徽章采用玩家范围效果唯一组，如 `sdbf:gem_badge`。是否禁止放入第二枚还是允许存放但只生效一枚，仍需物品与界面设计确认；API 应能支持两者。有效实例的选择顺序需稳定，其他副本明确提示重复失效。多个容器是否参与同一徽章的总分尚未决定，本草案的空间及分数读取范围先限定为当前容器；玩家范围唯一效果仍须覆盖全部佩戴容器。

建议提供 STARTUP 专用 `AstralFillers.disable(itemId)` 或等价配置开关，禁用默认的：

- `deeprealm_4th:warrior_medal`
- `deeprealm_4th:wayfarer_medal`
- `deeprealm_4th:warden_medal`

禁用后佩戴中的旧效果必须清除。配方、战利品、任务奖励、展示入口由整合包脚本相应移除。现存默认徽章物品的数据处理方式留待迁移设计。

攻击型转换继续使用已确认的分数压缩与品质效率分别计算后组合的方案。普通徽章到同种同核心的天然高品质徽章，在固定布局下，参考 +30% 攻击收益应提高到约 +39%–45%。具体曲线及多属性分配系数仍待模拟，不能直接套用内置战士勋章的倍率。


## 大数计分与稳定转换

建议新增不可变 `AstralNumber` 和 `BigScoreSheet`，用于逐颗节点及新徽章。接口需要：

```text
of(number or decimal/scientific string)
add, subtract, multiply, divide
pow(exponent), min, max, compare
ln, log1p, isZero, sign
toScientificString, toFullString, format
serialize, deserialize
```

基础 Writer 和本地 Writer 应接受 AstralNumber，来源结果返回同类型。KubeJS 示例须使用显式方法链，超大分数不能隐式转为 JavaScript Number 后再乘方。

实现可选择合适的十进制或尾数／指数表示，但需能表达超出 double 的有限分数，支持带符号的旧管线桥接数值、零值、差值及分数指数。本系统宝石规则输出非负分数；非法除零、无效幂次和非有限输入必须有明确诊断。

新徽章直接在大数类型上计算对数，再转换成有限 double 属性修饰。`ln(1+x)` 对很大 x 应避免先把 x 变成 Infinity，对很小 x 也应保持精度。B/F/Δ、比较及加工占比须使用同一套运算。

建议提供完整数字、分组数字、科学计数和紧凑单位等格式化选项，供整合包选择展示方式。缓存和同步保存可恢复的数值表达，不保存已经舍入的界面字符串作为计算输入。

## 展示与同步接口

建议共用填充物物品类配合可注册的 `FillerPresentation`：

```text
name(stackData) -> translated display name
summary(stackData) -> static rule description
tooltip(stackData, serverResultSummary) -> lines
optionalTintOrModel(stackData) -> presentation hint
```

名称、规则说明、天然与有效三维、主修饰字母、附加修饰都根据 NBT动态取得。同一物品 ID 的红宝石 α 与蓝宝石 β 应有各自信息，不采用一个共用固定说明。

服务端 `ResultSummary` 建议包含每格 kind/variant/rule、B/F/Δ/g、最终六分数、已选来源、当前条件、失效或异常原因。徽章摘要提供输入分数、分数压缩结果、品质效率、输出属性和操作类型。

界面／tooltip 读取服务端摘要；没有佩戴的容器可请求只读预览，不应用玩家属性。关闭格或失效填充物仍可查看真实保存数据。完整调试轨迹可按需请求，常规刷新使用较小摘要，避免每次同步全部候选图。

## 来源名单约定

为让字母化后的来源仍然明确，规则查找使用完整种类＋字母，普通物品 ID 过滤只用来确认这是共用填充物。

- **R**：当前规则表中角色为原生的合法宝石填充物，使用匹配的正分数类型。新原生主修饰需要进入规则表后才成为合格来源。
- **P9**：前九种已确认宝石中的加工主修饰固定名单。魔力钻石、龙石、穹玉晶石、紫晶石、砷铅铁矿石及充能红石的普通最终读分允许 R＋P9；魔力钻石 γ 额外允许魔力钻石 β。
- **PF**：福鲁伊克斯水晶 β、γ 的固定加工来源名单，等于 P9 排除福鲁伊克斯水晶 β、γ；再加 R。
- **本批默认**：待审 19 种普通读分使用 R；额外加工来源在下方规则表中写明。
- **基础读取**：原生身份、格子状态、附加修饰及 B 可以在最终分未完成时读取，不形成最终分依赖。表内仍按指定来源类别筛选。
- **泪宝石末端**：读取其他宝石的加工结果，排除所有泪宝石主修饰；其他主修饰的来源名单不包含泪宝石。

P9 固定名单如下。种类字段为原宝石种类，不是共用填充物的实际 ID：

- 粗制绿宝石 β，`tetra:pristine_emerald#beta`。
- 粗制青金石 β，`tetra:pristine_lapis#beta`。
- 粗制钻石 β，`tetra:pristine_diamond#beta`。
- 粗制紫水晶 β，`tetra:pristine_amethyst#beta`。
- 海晶砂粒 β，`minecraft:prismarine_crystals#beta`。
- 海晶砂粒 γ，`minecraft:prismarine_crystals#gamma`。
- 充能赛特斯石英水晶 β，`ae2:charged_certus_quartz_crystal#beta`。
- 充能赛特斯石英水晶 γ，`ae2:charged_certus_quartz_crystal#gamma`。
- 福鲁伊克斯水晶 α，`ae2:fluix_crystal#alpha`。
- 福鲁伊克斯水晶 β，`ae2:fluix_crystal#beta`。
- 福鲁伊克斯水晶 γ，`ae2:fluix_crystal#gamma`。
- 红宝石 β，`thermal:ruby#beta`。
- 红宝石 γ，`thermal:ruby#gamma`。

## 建议实施顺序

1. 完成每栈动态解析、NBT工具、CellView及动态 B，先证明相同 ID可分别处理不同宝石。
2. 完成本地分数、逐格结果、来源声明及依赖结算，再证明两级以上链条与复制行为。
3. 完成空间辅助、玩家快照、数据修改失效和运行时写回。
4. 完成大数类型、新徽章、玩家唯一组和旧勋章禁用。
5. 完成动态加工产物、客户端摘要、显示与双版本适配。
6. 通过验收后再确定参数、掉落分布、配方与强化机制，并进行收益模拟。

实现阶段应优先交付 API与最小可运行示例，随后再将整套宝石规则接入。本文保留已经确定的玩法约束，所有接口命名和未标定参数仍可在评审后调整。
